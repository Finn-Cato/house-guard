Dear Homey review team,

Thank you for the feedback. Candidate 0.4.43 shortens both Store readmes to two paragraphs, uses English as the default settings experience with Norwegian translations, replaces the app's logo-and-text Store image with a licensed house photograph, and adds a formatted title integrating the argument in “A fire or water alarm is active”. It is installed and running on Homey Pro. Actual English/Norwegian Homey webview rendering and physical end-to-end behavior still require verification; local tests are not a certification result.

The `homey:manager:api` permission supports House Guard's core alarm and household automation: discovering and monitoring selected sensors and residents, reading zones and Flows, and controlling selected light, lock, garage and water-control device capabilities. Timeline entries use the Apps SDK. A separate, local API-key session currently runs native Flow cards for ordinary/critical/image phone notifications, yes/no night questions, Sonos and presence/sleep actions, and starts the user's selected Flows.

A read-only check on 12 October 2026 from the installed 0.4.40 app's `HomeyAPI.createAppAPI` client reports actual `intersectedScopes` containing `homey.device.readonly`, `homey.device.control` and `homey.flow.readonly`, with neither `homey.flow` nor `homey.flow.start`. Version 0.4.43 keeps the same API permission and integration paths. The [official Flow API reference](https://athombv.github.io/node-homey-api/HomeyAPIV3Local.ManagerFlow.html#runFlowCardAction) requires these latter scopes for card execution and Flow starts. Historical app-client attempts returned `Missing Scopes` for action/condition cards, Flow starts and direct presence writes. The check confirms scope metadata only: it did not execute cards, start Flows, send messages or change presence. It does not establish successful app-only execution or delivery.

Our setup requests a dedicated key with **Flows permission only**, rather than All permissions. The current validator also accepts a broader key if supplied. Full Flow permission remains powerful: executing native/device cards can indirectly control devices and residents. The key is stored separately in app settings, used for the local Homey API, and excluded from configuration exports, status responses and logs. We do not claim encrypted-vault storage. Homey supports selecting key permissions and revoking keys in the Web App. [Homey API-key guide](https://support.homey.app/hc/en-us/articles/8178797067292-Create-and-use-API-Keys-on-Homey-Pro).

Could you confirm a supported app-only route for these operations, or how the app permission can obtain the required Flow scopes? We would prefer to remove the personal key, after verifying equivalent delivery and behavior. Removing it from the current implementation would disable these features; timeline notifications do not replace selected-recipient critical/image push or questions.

Individual normal/critical push and camera delivery were previously confirmed by a tester. On 12 October 2026, the operator also reported a water-sensor test. Read-only inspection of Homey Insights and House Guard 0.4.42 confirms one sensor's vendor alarm true/false, the matching incident/recovery, accepted critical/normal notifications and timeline entries. The water-control device reported OFF, but House Guard's shutoff was disabled at that time and issued no water command; it was enabled later. These logs cannot establish phone receipt or mechanical closure attributable to House Guard, and **we cannot yet confirm complete physical fire-unlock or House Guard water-shutoff end-to-end tests**. The candidate still needs the remaining sensor-to-phone and physical-action checks, including recovery and failure cases. Automatic release should be disabled before resubmission, with manual release held until the required tests pass. We have not verified the current dashboard setting and are not claiming it is already disabled.
